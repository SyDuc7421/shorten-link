01 · Tổng quan

Hai chương trình, ba dịch vụ phía sau

Cùng một codebase build ra hai binary. cmd/server phục vụ API và redirect. cmd/worker đọc sự kiện từ RabbitMQ rồi ghi vào MySQL. Server không bao giờ chờ worker: mọi liên lạc giữa hai bên đều đi qua hàng đợi.

02 · Đường nóng

Chuyện gì xảy ra khi mở GET /{code}

Đây là request quan trọng nhất: phải nhanh, và phải chạy được ngay cả khi một phần hệ thống chậm. Phần lớn redirect dừng ở Redis và không chạm tới MySQL. Lượt click được publish kiểu fire-and-forget nên redirect không chờ nó.

03 · Chạy nền

Worker đếm click theo batch

Nghìn click mỗi giây được gom lại thành vài lần ghi database. Worker lấy tối đa 500 sự kiện, hoặc bao nhiêu sự kiện tới trong 2 giây, cộng dồn theo mã, rồi ghi tất cả trong một transaction duy nhất.

04 · Bên trong server

Ba lớp, interface nằm ở phía dùng

Mỗi lớp chỉ biết lớp ngay dưới nó, qua interface nhỏ. Interface được khai báo ở package dùng nó, không phải package hiện thực nó. Vì vậy service không import repository, và test có thể thay bằng mock viết tay. Chỉ cmd/server và cmd/worker biết mọi package, vì đó là nơi lắp kiểu cụ thể vào interface.

Chuỗi middleware, từ ngoài vào trong

Thứ tự có ý nghĩa: metrics.Middleware nằm ngoài cùng nên request bị timeout vẫn được đếm là 503 với đúng route. metrics.RecordRoute nằm giữa bước 1 và 2, báo cho bước 0 biết pattern nào đã khớp.

  1. metrics.Middlewaređếm và đo thời gian theo method, route, status
  2. http.TimeoutHandlercắt request quá 10s
  3. SecureHeadersHSTS, CSP, X-Frame-Options, nosniff
  4. CORSchỉ cho origin trong ALLOWED_ORIGINS
  5. JWTAuthBearer hợp lệ → user ID vào context
  6. RequestIDnhận X-Request-ID hợp lệ hoặc tạo mới
  7. AccessLogmột dòng log mỗi request
  8. Recoverpanic → log kèm stack + JSON 500
  9. MaxBodySizebody quá 1 MB → 413
  10. RateLimitsliding window theo IP trên Redis → 429
  11. RequireAuthroute cần đăng nhập → 401
  12. RequireAdmin/api/admin/*, đọc MySQL mỗi request → 403

Short code sinh ra thế nào

Không dùng chuỗi ngẫu nhiên. idgen tạo Snowflake ID 64 bit gồm số mili giây từ 2024-01-01, node ID (0–1023) và số thứ tự (0–4095), rồi viết ở Base62 ra mã 10 ký tự. Mã chỉ duy nhất khi mỗi instance server có NODE_ID khác nhau.

Xác thực

Access token là JWT RS256 sống 15 phút, kiểm tra bằng public key mà không cần tra DB. Refresh token sống 7 ngày; jti của nó nằm trong Redis và bị GETDEL khi refresh, nên mỗi token chỉ dùng được một lần. Sai mật khẩu 5 lần thì email bị khóa 15 phút.

06 · Dữ liệu

Dữ liệu nằm ở đâu

MySQL: nguồn sự thật

  • users: email, password_hash, role, quota_daily, disabled_at
  • links: short_code (unique, utf8mb4_bin), original_url, clicks, expires_at
  • analytics_daily: click theo link theo ngày UTC
  • audit_log: mỗi thao tác admin một dòng
  • notifications: thông báo trong app, worker ghi

Redis: tra nhanh, sống ngắn

  • sl:<code>: URL gốc, ≤ 24h
  • rt:<jti>, urt:, urv:: phiên đăng nhập
  • lockout:<email>: số lần sai
  • prt*:: token reset mật khẩu, cooldown
  • rl:<action>:<ip>: cửa sổ rate limit

RabbitMQ: tách "bấm" khỏi "ghi"

  • Exchange topic shortlink
  • clicks ← link.clicked
  • notifications ← disabled, enabled, expiring, password_changed
  • shortlink.dlx → clicks.dlq, notifications.dlq
  • link.created chưa có consumer
07 · Khi có sự cố

Một phần chết thì phần nào còn sống

Đọc theo hàng: dịch vụ đó sập thì từng tính năng ra sao. Server không cần RabbitMQ để khởi động: publisher tự thử kết nối lại mỗi 2s. Worker thì thoát khi mất RabbitMQ, rồi được Docker khởi động lại.

08 · Quan sát (chỉ local)

Metric được kéo về, log được đẩy đi

make observe chạy server, worker và stack quan sát trong container. App không kết nối tới thành phần nào của stack: Prometheus tự kéo metric từ cổng /metrics riêng, còn log JSON in ra stdout được Alloy gom đi. Vì vậy stack có sập thì request cũng không bị ảnh hưởng.

Bản vẽ của docs/architect.md và docs/modules/. Khi code đổi, sửa các file đó trước rồi cập nhật trang này trong cùng commit.
